Episode 4. Pipelines, compute, platform basics and delivery


This episode covers ingestion strategy, metadata-driven frameworks, Spark Declarative Pipelines, the trouble with medallion dogma, compute selection, a set of platform basics that often come up as quick questions, and CI/CD. Kafka and streaming get their own episode next.

Ingestion strategy first. Headline: "I choose the pattern by source type and latency, but the principles stay the same." Four principles. Land raw data once, unchanged, in bronze. Make every load idempotent and restartable. Capture lineage metadata on every row: ingest time, source file or offset, and batch ID. And reconcile counts automatically. Then add the key line: "I run it through one framework with many configurations, not one pipeline per source."

Then the patterns by source. Files in cloud storage: Auto Loader, with file notification mode for high volume and schema evolution with a rescued data column. Operational databases: change data capture, through managed connectors, Azure Data Factory, or Debezium into Kafka. Small tables can use incremental JDBC with a watermark. Events: Structured Streaming from Kafka or Event Hubs, one checkpoint per stream, and an available-now trigger if near-real-time is enough. SaaS applications: a managed connector before hand-written API code. And historical bulk loads: a one-off bulk copy, then switch to incremental. Tie this to a real migration or history load you've run, with its scale.

Round it off with privacy: "We tokenise identifiers during ingestion, so raw values never spread." That's distinctive, so always say it.

Next, metadata-driven frameworks. Headline: "A small number of well-tested load patterns, driven by configuration, with observability built in. Adding a source should be configuration plus a review, not new code." Then the design. The config store: YAML in Git, which is reviewed and versioned, or Delta tables, which are queryable at run time. Many teams author in Git and publish to tables. The load patterns: full, incremental by watermark, append, change data capture merge, and slowly changing dimension type two. Each pattern is one tested component. Orchestration follows the config, for example a for-each task in Workflows. Quality, tokenisation and retention rules are declared per object. And observability: a run log, row counts, checksums, reconciliation and alerts.

Then the honest part: the pitfalls. Config sprawl, too many options, hard debugging, and a framework only one person understands. "So I keep the patterns few, and leave an escape hatch for custom code." That kind of self-awareness scores well.

A typical control-table design: a source registry, an object config table, and a run log. One generic loader. Counts written back on every run, and mismatches fail the load and alert.

Now Spark Declarative Pipelines. That's the open-source name for what Databricks sells as Lakeflow Declarative Pipelines, previously Delta Live Tables. Headline: "The big decisions are streaming table or materialized view for each dataset, how to split pipelines, where data quality rules live, how to handle change data capture, and when not to use declarative pipelines at all."

Streaming tables for append-only, incremental sources where each record is processed once, so bronze and most silver. Materialized views for joins and aggregations that must reflect upstream changes. One pipeline per domain or data product, not one giant pipeline. Expectations for data quality, choosing warn, drop or fail per rule, and a quarantine table rather than failing a whole run. AUTO CDC for slowly changing dimensions, with a sequencing column for out-of-order changes. Protect bronze from full refresh, because if the source has already expired data, like Kafka retention, a full refresh loses history. Triggered mode for most workloads; continuous only when latency really needs it. Serverless pipelines by default. And when not to use it: heavy custom control logic like your framework, complex orchestration across non-Databricks systems, or unusual write patterns. Then use jobs with Structured Streaming and foreachBatch.

Medallion dogma. This is an opinion question, and they want an opinion. Headline: "Medallion is a useful vocabulary, not a law. I treat the layers as quality contracts, not three mandatory copies." Then the problems. Copy explosion: three physical copies triples storage and pipelines. Privacy cost: personal data in bronze, silver and gold means three places to purge under privacy law, so tokenise early and keep fewer copies. Not every dataset needs every layer, which is why an archival platform can have a deliberately thin gold layer. Use views where you can. Layer names hide meaning, so define each layer's contract: its quality, schema and ownership guarantees. Silver becomes a dumping ground, and gold sprawls into one table per report, so design gold around data products, not dashboards. And in a data-mesh model, each domain owns its own layers.

Compute selection. Headline: "I start from the workload pattern, then weigh start-up time, cost, control and isolation. My default is serverless, and I need a reason to choose classic." Then your proof: a real example of moving a workload, such as SQL warehouses, from classic to serverless, and what it changed.

By workload. BI and SQL: a serverless SQL warehouse. Scheduled ETL: serverless jobs, or classic job compute when you need custom libraries, init scripts, specific instances or strict networking. Declarative pipelines: serverless. Interactive development: serverless notebooks or shared clusters with policies, and never production on all-purpose compute, because it's billed at a higher rate and isn't isolated. ML training: classic compute with the ML runtime, GPUs if needed. Then cost levers: Photon where it pays back, spot instances for workers, auto-termination, and cluster policies to cap size.

Now a set of platform basics. These often come up as quick questions, so have one or two sentences ready for each.

Control plane and compute plane. The control plane is Databricks-managed: the web app, the jobs scheduler, notebooks and Unity Catalog services. The compute plane runs clusters: classic compute in the customer's cloud account, serverless compute in Databricks' account. Data stays in customer storage either way.

Workspace design. Usually one Unity Catalog metastore per region, workspaces separated by environment, sometimes by business unit, and catalogs per environment and domain, bound to workspaces. Isolate with catalogs and workspace binding rather than dozens of workspaces.

Managed versus external tables. Managed tables let Unity Catalog control storage and lifecycle, and they unlock predictive optimization; dropping one deletes the data. External tables live at a path you manage; dropping removes only metadata. Recommend managed by default, external when other engines must write the same files.

Delta Sharing is an open protocol for sharing live tables, views, volumes and models without copying. UniForm lets a Delta table also be read as Iceberg, so engines like Snowflake or Trino can read it. System tables hold audit logs, billing, lineage, query history and job runs, and they're the basis for cost and security reporting.

DBUs. A Databricks Unit is a unit of processing per hour, priced by compute type and tier. Total cost is DBUs plus cloud VM cost on classic compute, while serverless includes the VMs. With a client, steer the conversation from price per DBU to cost per pipeline and time to insight. And to control cost: tag everything and report from billing system tables, use cluster policies and auto-termination, job compute and serverless instead of all-purpose, Photon where it pays back, right-sized SQL warehouses, and budgets with alerts.

Disaster recovery. Define recovery point and recovery time objectives first, replicate with deep clone, keep workspace configuration in Terraform and bundles so it can be redeployed, and test failover.

Finally, CI/CD. Headline: "I separate infrastructure from workloads." Terraform manages workspaces, Unity Catalog, grants, policies and networking. Bundles define jobs, pipelines and apps per environment. Code goes through pull requests and automated tests, deploys to test, passes an approval gate, then the same bundle deploys to production as a service principal. Build once, deploy many. No personal tokens. Secrets in Key Vault-backed scopes. Rollback by redeploying the previous bundle, and Delta time travel or restore for data issues. And your proof: a pipeline you built or run, and how many teams release through it.

Practice question. Pause and answer out loud: "A client wants every new data source onboarded in days, not weeks. How would you design for that?"
(Pause: answer out loud.)
Model answer. A metadata-driven framework: a small set of tested load patterns, with each source described in configuration, reviewed in Git and published to control tables. Orchestration generated from the config, quality and privacy rules declared per object, and reconciliation and alerts built in. Onboarding becomes a config change plus a review. And keep an escape hatch for the odd source that needs custom code.
