Episode 6. Governance, security and networking


This is home ground for you. Your privacy and governance work is your strongest differentiator, so this episode is about saying it crisply. We cover Unity Catalog, row filters and attribute-based access, Databricks Apps authentication, tokenisation, enterprise governance strategy, multi-region design, and Azure networking: VNet injection and Private Link.

Start with Unity Catalog. "What does Unity Catalog give you beyond the Hive metastore?" Headline: "One governance layer for everything, across workspaces." Then the list: one account-level metastore per region shared by workspaces, a three-level namespace of catalog, schema and object, fine-grained grants, row filters and column masks, governed tags and attribute-based access control, automatic lineage, audit through system tables, volumes for files, governance for models and functions, and Delta Sharing.

Row filters and column masks are SQL functions attached to tables, usually checking group membership with is account group member. The cost is a function evaluated per row, so keep the logic simple.

"Why move from role-based to attribute-based access control?" Headline: "Because per-table rules don't scale." With thousands of tables, per-table grants and filters become sprawl. Attribute-based access control uses governed tags, like PII equals true or sensitivity equals high, and policies defined once at catalog or schema level. Newly tagged tables are protected automatically.

Databricks Apps authentication. This is likely in both interviews. "On-behalf-of the user versus service principal: how do row filters behave?" With a service principal, the app queries as itself, so every user sees what the app sees, and you'd have to rebuild security inside the app. With on-behalf-of-user authorization, the app passes the user's identity, so Unity Catalog grants, row filters and masks apply per user automatically. "That's why I used on-behalf-of: governance stays in one place."

Tokenisation. "Why deterministic tokenisation, and what are the risks?" Deterministic tokens let analysts join and count across tables without seeing raw identifiers. The risk: the same input always produces the same token, so low-entropy values like phone numbers are open to dictionary or frequency attacks. The mitigation: keyed tokenisation, like an HMAC, with the key held in HashiCorp Vault, strict access to detokenisation, and audit. Follow-up: "What happens when you rotate the key?" All tokens change, so every join breaks unless you re-tokenise. Options: versioned keys with a key ID stored alongside the token, a bulk re-tokenisation programme, or a token vault mapping.

Now enterprise governance strategy. Headline: "Governance is an operating model first and a tool second. A central platform team sets the guardrails in Unity Catalog, and domain teams own their data within them." Then seven elements. Operating model: federated. Catalog design: by environment and domain, bound to workspaces. Identity: SCIM from Entra ID, grants to groups not individuals, service principals for jobs, no personal tokens in production. Classification and policy: governed tags, attribute-based policies, filters and masks, and tokenisation. Lifecycle: retention rules and automated purging, with a rule on every data object. Evidence: lineage, audit and access logs from system tables. And trust: quality checks and certified datasets.

Multi-region design. The key facts. A Unity Catalog metastore is regional, so each region has its own, and workspaces attach to their region's metastore. Identity is account-level, so groups and service principals are the same everywhere. Because metastores are separate, catalogs, grants, tags and policies must be deployed as code, with Terraform, to every region. Regulated data stays in its home region, and you share permitted data with Delta Sharing rather than copying. For disaster recovery, define recovery point and recovery time objectives first, replicate with deep clone or a Delta-aware process, because plain storage replication can copy the log and data files inconsistently, redeploy workspaces from code, and test the failover. And watch cross-region egress cost. One-line summary: "Identity is account-wide; metastores are regional."

Now networking. This is where many data people are weak, so a clear answer stands out. The one sentence to remember: "VNet injection decides where your clusters live. Private Link decides how traffic reaches a service." A fully private deployment needs both, plus secure cluster connectivity.

VNet injection. By default, Azure Databricks creates the compute network for you in a locked resource group. With VNet injection, you deploy the classic compute plane into a virtual network you own. You provide two subnets, the host subnet and the container subnet, both delegated to Databricks, each with a network security group. Every cluster node takes one IP address in each subnet, and Azure reserves five per subnet, so a slash twenty-four supports about two hundred and fifty-one nodes. Size for peak concurrent nodes, because running out of IPs makes clusters fail to start. Clients want injection to route egress through their own firewall, peer to hub networks, reach on-premises sources over ExpressRoute, and meet security policy.

Secure cluster connectivity, also called no public IP. Cluster nodes have no public IPs and no open inbound ports. Each cluster opens an outbound connection to a relay in the control plane. Because nodes have no public IP, they need a stable outbound path: usually a NAT gateway, or a firewall with user-defined routes.

Private Link has three kinds. Front-end: users to the workspace UI and API, through a private endpoint, often in a transit network reached over ExpressRoute or VPN. It also needs a browser authentication endpoint per region for single sign-on. Back-end: clusters to the control plane, through a private endpoint in the workspace network. It requires VNet injection and secure cluster connectivity. And storage: private endpoints for ADLS, with separate DFS and blob endpoints, and for Key Vault, so storage can have public access turned off. Serverless compute is different: it runs in Databricks' account, so it reaches your storage through private endpoints created by a network connectivity configuration, which you approve.

DNS is where private deployments usually break. A private endpoint only works if the name resolves to its private IP. Each service needs a private DNS zone, like privatelink dot azure databricks dot net, linked to the networks that use it, and on-premises DNS must forward those zones to Azure.

Two troubleshooting questions you should be ready for. First: "Clusters stopped starting after the client locked down egress." Check firewall rules for the Databricks service tags, user-defined routes, network security group rules, DNS resolution of private endpoints, and whether the subnets have run out of IPs. Second: "Users can't open the workspace after front-end Private Link was enabled." Check that the workspace name resolves to the private IP from the user's network, that the browser authentication endpoint exists, the ExpressRoute or VPN routing, and the workspace's public access setting.

One action before the interview: know how your current platform is set up. Is the workspace VNet-injected, is secure cluster connectivity on, is Private Link front-end or back-end, how does egress work, and how is DNS handled. Even if another team owns the network, an architect is expected to know.

Practice question. Pause and answer out loud: "What's the difference between VNet injection and Private Link?"
(Pause: answer out loud.)

Model answer. VNet injection puts the classic compute plane into a network the customer owns, so they control routing, firewalls and peering. Private Link replaces public endpoints with private IPs, so traffic to the workspace, the control plane or storage stays on private networks. Injection is about where compute lives; Private Link is about how traffic gets to services. A fully private deployment uses both, plus secure cluster connectivity.
